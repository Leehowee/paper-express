# 语义与证明依赖审查

## 检查到的究竟是什么

展开关键定义，确认命题没有变成空集合上的全称、矛盾前提的推论、把结论作为参数的循环条件句，或与论文无关的数值特例。所有应用义务都应在返回信息中可定位。

参数化引理可以合法地假设“每步下降”并推出整条轨迹的下降；这只验证组合逻辑。具体算法仍需独立证明每步关系。模板的二次目标示例展示了如何完成这一步实例化。

## 检查完整依赖

对入口使用 `#print axioms`，查看传递依赖，而非只搜索当前文件。`sorry` 和 `admit` 可以留下占位依赖；导入文件也可能引入未完成证明。新增公理必须逐项披露，不能把待证事实提升为公理。

Lean 常用基础公理 `propext`、`Classical.choice` 和 `Quot.sound` 与研究者临时加入的假设性质不同。报告实际集合，不使用含糊的“零公理”宣传一般 Mathlib 证明。

`native_decide` 等信任扩展、元程序、编译求值桥接和跳过检查的设置，需要单独记录与审查。标准战术生成并由内核检查的证明项，与依赖外部执行可信性的证书分别处理。确需更强独立验证时，核对当前版本支持的重检工具并执行；没有执行就不宣称做过。

## 运行记录与源码对应

检查日志必须对应当前源码、锁文件和工具链。修改后旧日志不再证明当前工程通过。构建完成后检查定理确实在构建入口内，审查文件确实导入它们，且没有把失败的命令输出隐藏在另一条成功命令之后。

本模块的验证脚本检查常规构建、显式审查入口、常见未完成标记及公理输出，仍需人工或代理审查语义、元编程与额外假设。依据见 [官方资料](../../references/lean-sources.md)。

## 允许写进论文的结论

| 当前状态 | 可以陈述 |
| --- | --- |
| 数学证明完整，Lean 未运行 | 已给出数学证明，形式化检查尚未完成 |
| 条件引理已通过，方法条件待证 | 已验证该条件引理，当前算法的应用仍有义务 |
| Lean 通过，但对应关系未审查 | 编码命题已检查，论文覆盖尚未确认 |
| 证明、检查、依赖和对应均完成 | 在列明条件及覆盖范围内，形式化命题已验证 |
| 有占位、额外未证公理或检查失败 | 证明未完成或检查未通过 |
