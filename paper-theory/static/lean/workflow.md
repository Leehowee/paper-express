# Lean 形式化工作方式

## 固定可复查环境

优先使用已有工程，记录 `lean-toolchain`、`lakefile.toml` 或 `lakefile.lean`、`lake-manifest.json` 和实际版本。新任务可复制 [示例工程](../../assets/lean-project/lakefile.toml) 到任务目录。该工程固定 Lean/Mathlib 版本用于复现，不声称是最新版本；更换版本后重新检查。

依赖下载与证明检查分别处理。已有锁文件时先按锁定依赖构建，不为一次验证无故升级库。首次准备缺失依赖后保存实际锁文件。若需要官方缓存，只获取相关模块；下载成功不等于定理通过。

## 先建立语义表

| 论文内容 | Lean 编码 | 必须核查 |
| --- | --- | --- |
| 变量与维度 | 类型、`Fin n`、矩阵或函数 | 行列顺序、实数或复数、有限维条件 |
| 可行集 | 集合或带证明的子类型 | 非空、成员条件、退化情况 |
| 目标与算法 | 定义和递归更新 | 优化方向、归一化、更新顺序 |
| 假设 | 显式参数、结构字段或已证明引理 | 不是隐藏的待证结论；应用条件是否已完成 |
| 命题 | 带完整量词的定理类型 | 全称、存在、极限、概率及比较对象 |
| 实现 | 单独的对应证明或误差模型 | 浮点、近似、随机、提前停止 |

## 从小引理到主定理

优先复用已存在、类型匹配的 Mathlib 定理，查看实际定义与假设，不能凭名称猜测含义。先证明可行性、维度和基础不等式，再处理最优性、极限或概率结论。复杂路线可分阶段交付，但阶段之间的缺口必须可见。

证明草稿中的未完成义务记录在清单中。若为探索暂时使用 `sorry` 等占位，该分支保持未完成状态，不能进入已完成工程。不要用 `axiom`、结论参数或不相关的弱命题代替当前主定理。

## 构建与审查

在工程目录执行：

```text
lake env lean --version
lake build
lake env lean Audit.lean
```

`Audit.lean` 导入实际成果模块，并对需要交付的入口逐一执行 `#print axioms`。保存源码与锁文件散列、命令、退出码和日志；检查未完成证明及额外公理。可使用 [验证脚本](../../scripts/verify_lean.py) 收集这些结果。

脚本属于常规构建和依赖检查，不替代源码审查或语义对应。对包含元编程、替换内核检查选项或额外信任机制的工程，按 [依赖审查](integrity.md) 决定是否需要独立重检；不要只看“构建成功”。

验证脚本同时返回 `build_status`、`lean_status` 和证明依赖状态：未启动构建为 `source_unrun`；已启动但构建或依赖审查未通过为 `check_failed`；所列入口全部通过才为 `checked`。原有 `status: checked / not_cleared` 保留为脚本整体结果。环境探测失败不等于数学命题被否定；缺少语义映射时，即使脚本检查通过也不能转为完整算法保证。

## 把结果放回论文

记录哪些入口覆盖哪个命题，以及哪些参数仍是外部假设。完成论文—Lean 对应后，再决定正文可以使用的保证。固定输入上的计算证书、抽象条件引理和覆盖所有允许输入的算法定理分别表述。

环境失败时记录具体原因，不反复修改数学命题来绕过工具问题。能完成的数学推导和源码继续交付，Lean 状态保持未运行或失败。
