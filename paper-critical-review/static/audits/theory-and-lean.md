# 理论与 Lean 审查

从论文声称的保证出发，依次检查对象、假设、证明和实际用途。仅当论文提出数学保证，或用户要求专门理论审查时加载；不要求每篇经验论文补一套理论。

## 命题是否就是论文需要的结论

定位命题与其引用处，展开量词、维度、定义域、概率空间和成立条件。检查“存在”与“任意”、“目标值”与“迭代点”、“驻点”与“全局最优”、“训练目标”与“下游指标”、“有限样本观察”与“泛化保证”的区别。

明确原问题、连续松弛、子问题和离散输出之间的关系。若理论证明内层精确求解下的性质，而算法使用近似、随机、截断或有限迭代，要求给出适用说明、误差控制，或缩小保证范围。

## 推导是否有效

- 每个关键步骤依赖什么条件，条件是已证、明示假设还是尚待确认？
- 逆矩阵、谱分解、梯度、交换极限、期望或优化次序时，所需条件是否满足？
- 单调且有界只保证相应实数序列收敛；不能据此推出迭代点收敛或全局最优。
- 更大可行域、可重参数化、无额外超参数、经验多次同解等事实，是否被过度解释？
- 泛化界中的样本独立性、学习后的模型选择和数据依赖量是否与实际过程一致？

必要时构造满足假设的低维反例。反例必须逐项核实前提，说明否定的是哪个命题；在不满足前提的情形失败，只能说明适用边界。

## 形式化是否忠实

记录原命题、Lean 声明、编译环境、版本、命令和日志的实际检查范围。独立查看以下三层：

1. **构建**：是否运行、入口是否包含声称的文件、是否成功。
2. **证明完整性**：占位证明、`sorryAx`、自引入公理、额外假设和依赖是否披露；合理基础公理与把结论直接假设为真要区分。
3. **语义覆盖**：编码的对象、量词、算法和结论是否匹配论文，通用引理的应用条件是否在当前方法中得到证明。

已编译的条件命题不能替代缺失的应用条件。源文件里没有 `sorry` 字样也不足以保证整个依赖链无占位。没有运行环境则保留未运行状态，不推定验证失败。

复用第三部分的状态：`mathematical_status = candidate / proof_draft / proved / gap / refuted`，`lean_status = not_formalized / source_unrun / check_failed / checked`。`checked` 仅描述对应构建记录，必须同时看 `proof_integrity`、`semantic_mapping` 和 `application_obligations`。

原命题被否定与修订命题成立分别记录。一个未运行的辅助引理可标为 `source_unrun`，而它未编码的算法保证仍为 `not_formalized`；审查报告要指明状态属于谁。脚本状态与论文主张的支持状态不能互相替代。

## 关闭问题的依据

有效补证、满足前提的修改算法、明确误差项，或同步收缩论文主张均可解决相应问题。删除不成立保证后要重新评价剩余贡献，不能把“原保证已撤回”写成“原保证已验证”。修复工作经 [理论接口](../../interfaces/modules.md) 返回第三部分。
